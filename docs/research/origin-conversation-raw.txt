I actually think this is the pivotal question. It changes the product from "better documentation" to "capturing information that cannot be recovered from source code."

The better agents become at reading code, the less valuable descriptive documentation becomes.

Imagine an agent in 2030. It can:

read 500k LOC in seconds,

build an accurate call graph,

infer control flow,

identify invariants,

execute tests,

inspect git history,

run the application,

compare branches,

even infer architecture reasonably well.

What information is still missing?

That is where documentation should live.

A thought experiment

Suppose I ask an agent:

"How does authentication work?"

Today, we would expect it to read docs/auth.md.

A future agent probably won't.

It will simply inspect:

middleware
↓
JWT verification
↓
tenant resolution
↓
authorization
↓
request handlers

and answer perfectly.

Now ask instead:

"Why is authentication split into verification and authorization instead of a single middleware?"

That answer is almost never recoverable from code.

I think there are two categories of information
Recoverable information

Information that a sufficiently capable agent can derive.

Examples:

call graphs

dependency graphs

module boundaries

API endpoints

configuration defaults

data flow

state machines

algorithm implementation

which function calls another

retry count

timeout values

SQL schema

These should almost never be manually documented.

If they are, they'll drift.

Instead:

derive them

or

reference them.

Non-recoverable information

Information that existed only in someone's head.

Examples:

why

intent

tradeoffs

constraints

assumptions

business rules

organizational context

historical accidents

acceptable compromises

These are the things that disappear when people leave.

These are what documentation should preserve.

I would almost define documentation differently

Instead of

documentation explains the system

I'd define it as

documentation explains everything that cannot be inferred from the system.

That is a radically different philosophy.

Let's enumerate those gaps

I think they fall into surprisingly few categories.

1. Intent

The biggest one.

Example

TypeScript
if (cacheAge < 7)

The code tells me

seven.

Documentation tells me

We intentionally use seven because payment processors can take up to five days to reconcile. Two additional days avoid race conditions.

Intent answers

What were we trying to accomplish?

2. Tradeoffs

Example

Why PostgreSQL instead of DynamoDB?

The code never tells you.

Even if the commit message does, finding it is difficult.

Tradeoffs answer

Why this design over the alternatives?

3. Constraints

Example

IDs cannot exceed 63 characters.

The code enforces it.

But why?

Documentation explains

AWS IAM role names are limited to 64 characters, and we reserve one character internally.

The code cannot infer external constraints.

4. Assumptions

Example

Requests are processed in order.

Why?

Because Kafka ordering is guaranteed only within a partition.

That assumption exists outside the code.

5. Invariants

This one's interesting.

Code enforces some invariants.

But not all.

Example

A user must never belong to two active subscriptions.

The database may not enforce it.

Tests may not cover it.

It's still a business invariant.

6. Domain concepts

Code has

Invoice
Order
Reservation
Session

But...

What's the difference between

Reservation

Booking

Hold

Tentative reservation

Confirmed reservation

Only humans know.

7. Vocabulary

Agents struggle more than humans here.

Example

Project
Organization
Tenant
Account

Are those synonyms?

Hierarchy?

Different names historically?

A glossary helps enormously.

8. Decision history

Not every decision.

Only irreversible ones.

Example

We use optimistic locking.

Reason:
Database replicas introduce too much latency for pessimistic locks.
9. Failure philosophy

This is huge.

Example

Why retry?

Why fail fast?

Why ignore?

Why compensate?

Code shows behavior.

Not philosophy.

10. Operational knowledge

Example

If Redis fills up

Do X.

If queue latency exceeds 20 seconds

Ignore.

This isn't code.

11. Ownership

Code can't infer

Who owns this?

Who understands it?

Who approves changes?

12. Stability guarantees

Example

This interface is internal.

You may freely refactor it.

versus

This endpoint is a public contract.

The code doesn't distinguish.

13. Confidence

This is underrated.

Imagine

This parser probably works.

Nobody understands it.

Do not modify casually.

That's incredibly valuable.

14. Known weirdness

Example

This looks wrong.

It is intentionally wrong.

Reason:
Chrome 108 bug.

Every engineer has seen this.

Something interesting emerges

They're describing

My favorite emerging principle

I think this could become almost the mission statement of the framework:

Code explains what the system does. Documentation preserves why the system is this way.

Or, extending it slightly:

Anything an ideal agent could recover from code should not be manually documented. Documentation should capture the information that would otherwise disappear if every engineer who built the system left tomorrow.

I think that's a much stronger foundation than "self-healing docs." It gives the framework a clear philosophy: it is not trying to compete with increasingly capable code-understanding agents. It is trying to preserve the latent knowledge that those agents, no matter how capable, cannot infer because it was never encoded in the software in the first place.

=== [2] ASSISTANT (25775 chars) ===
Yes. At this point, I would think of it as a complete documentation operating system for agents, not as a Markdown convention or a Neo4j integration.

The framework needs to solve five different problems:

What knowledge is worth preserving?

How is that knowledge represented?

How do agents discover and use it?

How do agents create and maintain it correctly?

How does the system detect when the knowledge base is degraded?

Those are separate concerns. The mistake would be to solve all of them with one annotation syntax or one graph database.

The full stack

I would divide the framework into ten major bricks.

1. Philosophy and quality model
2. Knowledge ontology
3. Authoring language
4. Knowledge graph and indexes
5. Source-code integration
6. Agent skill and runtime interface
7. Linters and validators
8. Change-impact and maintenance engine
9. Repository workflows
10. Governance and observability

Each layer should have a narrow responsibility.

1. Philosophy and quality model

Before syntax or tooling, the framework needs a doctrine.

Otherwise agents will generate technically valid but useless documentation.

The central rule could be:

Document information that cannot be reliably reconstructed from the repository itself.

That includes intent, constraints, tradeoffs, invariants, domain meaning, risks, guarantees, and historical context that still affects present behavior.

It usually excludes:

call graphs,

file descriptions,

parameter lists,

obvious control flow,

copied configuration values,

descriptions that simply restate code.

Quality dimensions

The framework should formally define what “good” means.

A documentation item could be evaluated across:

Information gain
Relevance
Authority
Traceability
Scope clarity
Freshness
Non-redundancy
Actionability
Confidence
Discoverability

For example:

YAML
quality:
  information_gain: high
  authority: canonical
  evidence_strength: medium
  confidence: high
  scope_clarity: explicit

Not every item needs explicit scores, but the framework should use these concepts internally.

The negative definition

The framework should also explicitly identify anti-patterns:

Restating implementation
Speculating about intent
Documenting temporary code structure
Copying source-derived values
Creating multiple canonical explanations
Writing broad essays without scope
Recording decisions without consequences
Recording historical context that no longer matters

This philosophy must be embedded in every agent instruction and linter.

2. Knowledge ontology

The ontology defines the kinds of knowledge the framework understands.

This is probably the most important design artifact.

The first version should remain small. Too many concepts will make authoring burdensome.

First-class knowledge types

I would start with these:

Intent

What outcome was the system designed to produce?

YAML
type: intent
id: payments.retry-policy.intent
statement: >
  Increase successful payment capture without creating duplicate charges.
Constraint

What limits the solution space?

YAML
type: constraint
id: payments.processor-idempotency-window
statement: >
  The payment processor only guarantees idempotency for 24 hours.
source:
  - external-contract: processor-api-v3
Assumption

What is believed to be true but may not be enforced?

YAML
type: assumption
id: orders.events-partitioned-by-order
statement: >
  All events for an order are delivered through the same partition.
Invariant

What must remain true?

YAML
type: invariant
id: billing.single-active-subscription
statement: >
  An account must never have more than one active subscription.
Decision

What choice was made?

YAML
type: decision
id: auth.stateless-access-tokens
statement: >
  Access-token validation remains stateless.
Tradeoff

What was accepted or sacrificed?

YAML
type: tradeoff
id: auth.revocation-latency
statement: >
  Stateless validation accepts up to five minutes of revocation latency
  in exchange for avoiding a database read on every request.
Rejected alternative

What plausible option was considered and rejected?

YAML
type: alternative
id: auth.database-session-check
status: rejected
reason: >
  It introduced an unacceptable dependency on the session store for
  every authenticated request.
Domain concept

What does a term mean in this system?

YAML
type: concept
id: fulfillment.reservation
definition: >
  A temporary allocation of inventory that has not yet become an order.
Guarantee

What can consumers rely on?

YAML
type: guarantee
id: api.webhook-ordering
statement: >
  Webhooks are ordered per account, but not globally.
Risk

Where is the system fragile or surprising?

YAML
type: risk
id: reconciliation.non-idempotent-legacy-path
statement: >
  Replaying legacy reconciliation jobs can duplicate ledger annotations.
Known anomaly

What looks wrong but is intentional?

YAML
type: anomaly
id: exports.one-day-overlap
statement: >
  Export windows overlap by one day to account for late-arriving records.
Operational heuristic

What practice is useful but not a hard rule?

YAML
type: heuristic
id: queue.backlog-triage
statement: >
  Backlogs under ten minutes usually self-correct and should not trigger
  manual replay.
Ownership

Who has authority or relevant context?

YAML
type: ownership
id: auth.domain-owner
team: identity-platform
Confidence or uncertainty

What is not fully understood?

YAML
type: uncertainty
id: legacy.parser-order-dependency
statement: >
  The parser appears to depend on insertion order, but this has not been
  conclusively verified.
Relationships

The ontology also needs a controlled relationship vocabulary.

APPLIES_TO
MOTIVATES
CONSTRAINS
JUSTIFIES
ENFORCED_BY
PARTIALLY_ENFORCED_BY
VERIFIED_BY
VIOLATED_BY
DEPENDS_ON
ASSUMES
SUPERSEDES
REJECTS
QUALIFIES
CONTRADICTS
RISKS
OWNED_BY
DEFINED_IN
VALID_DURING

Example:

Constraint
  ──CONSTRAINS──> Decision

Decision
  ──JUSTIFIES──> Code symbol

Invariant
  ──ENFORCED_BY──> Database constraint

Invariant
  ──VERIFIED_BY──> Test

Tradeoff
  ──QUALIFIES──> Decision

This is where the graph becomes useful.

3. Authoring language

The authoring interface should optimize for three audiences:

engineers,

agents,

tooling.

Markdown with structured metadata is likely the right starting point.

A custom standalone language would create too much friction.

Two authoring modes

The framework should support both:

Narrative documents

Useful for explanations where several knowledge items belong together.

Markdown
---
id: auth.token-strategy
type: rationale
authority: canonical
scope:
  domain: authentication
---

# Token strategy

@intent auth.token-strategy.performance
Token validation must not depend on a synchronous database lookup.
@end

@decision auth.stateless-validation
Access tokens are validated statelessly.
@end

@tradeoff auth.revocation-delay
We accept a maximum revocation delay of five minutes.
@end

@constraint auth.multi-region-latency
A central session lookup would add cross-region latency to every request.
@end
Atomic knowledge records

Useful for programmatic maintenance and small facts.

YAML
id: auth.revocation-delay
type: tradeoff
statement: >
  We accept a maximum revocation delay of five minutes.
applies_to:
  - symbol:auth.verifyAccessToken
  - concept:auth.access-token
supports:
  - decision:auth.stateless-validation

Narrative files could compile into atomic records.

Required metadata

Every meaningful item should have:

Stable ID
Type
Statement
Scope
Status
Authority level
Applies-to references
Owner or ownership domain

Some types should require additional fields.

A decision should require:

Context
Chosen option
Alternatives
Consequences
Status

An invariant should require:

Statement
Scope
Criticality
Enforcement
Verification

An assumption should require:

Statement
Evidence
Failure consequence
Review trigger
Stable references

References should prefer semantic identities:

symbol:payments.RetryPolicy.calculateDelay
concept:billing.subscription
decision:auth.stateless-validation
config:auth.accessTokenTtl
schema:public.orders.status
test:auth.token-revocation
external:stripe.idempotency-policy

File paths may be recorded as resolution hints, but they should not be the identity.

Status model

Knowledge needs a lifecycle.

draft
active
contested
deprecated
superseded
historical
invalid
unknown

“Contested” and “unknown” are important. The framework should permit unresolved knowledge rather than encouraging agents to fabricate certainty.

The repository should remain the source of truth.

The framework should support questions like:

5. Source-code integration

The framework must understand enough about the repository to connect knowledge to implementation.

It does not need to understand everything.

Code indexing

Use language tooling such as:

language servers,

tree-sitter,

compiler APIs,

package manifests,

schema parsers,

configuration parsers,

test discovery.

The index should expose:

Symbols
Public interfaces
References
Call relationships
Imports
Ownership boundaries
Schemas
Config keys
Tests
Executable examples
Semantic attachment

Documentation items can apply to:

YAML
applies_to:
  - symbol:auth.verifyAccessToken
  - namespace:auth.middleware.*
  - service:identity-api
  - schema:public.sessions
  - path:src/auth/**

Scope must support different granularities.

Evidence strength

A knowledge item should identify how strongly it is connected to implementation.

YAML
enforcement:
  - ref: schema:public.subscriptions.unique_active_account
    strength: hard

  - ref: test:billing.single-active-subscription
    strength: regression

  - ref: symbol:billing.createSubscription
    strength: partial

This distinction matters because code may only partially enforce a documented invariant.

6. Agent skill and runtime interface

The skill is the primary interface between agents and the framework.

It should not simply say, “Read the docs.”

It should teach a protocol.

I would separate it into several agent capabilities.

A. Investigate

Before making a change, the agent invokes something conceptually like:

docs.context(
  task="change token revocation behavior",
  targets=["symbol:auth.verifyAccessToken"]
)

The result should be compact and ranked:

Relevant intent
Relevant invariants
Applicable constraints
Active decisions
Known risks
Rejected alternatives
Canonical concepts
Unresolved uncertainties

The skill should instruct the agent:

Read code first.

Use docs for non-recoverable context.

Treat canonical active knowledge as authoritative unless contradicted by reality.

Surface conflicts rather than silently choosing.

Do not treat historical items as current guidance.

B. Propose documentation

When the agent encounters missing context, it should decide whether documentation is warranted.

The skill should ask:

Would another capable agent be able to recover this from code?

Will this information matter for future decisions?

Is it stable enough to preserve?

Is it already documented canonically?

Can it be attached to a clear scope?

Is the agent observing intent, or merely guessing intent?

An agent should not document inferred intent as fact.

Instead:

YAML
type: uncertainty
statement: >
  The behavior appears intended to preserve ordering, but no confirming
  decision record was found.
C. Verify

The skill should define how to verify knowledge.

For each item:

Confirm its scope still exists.
Check whether its supporting evidence changed.
Check whether the statement still matches current intent.
Check whether authority or ownership changed.
Check whether a more canonical item supersedes it.
Check for contradiction or duplication.
Record confidence and evidence.
D. Refactor documentation

Agents need an explicit protocol for:

merging duplicates,

splitting overloaded documents,

superseding decisions,

moving contextual text to canonical concepts,

converting implementation descriptions into source-derived references,

archiving historical material.

E. Complete a task

Before declaring work complete, the skill should require:

Resolve high-confidence impacted documentation items.
Record “no documentation impact” with reasoning when appropriate.
Add new knowledge only when information gain is meaningful.
Do not create speculative rationale.
Run documentation validation.
7. Linters and validators

There should be both deterministic and agentic linting.

These are complementary.

Deterministic linter

It should catch things that can be proved mechanically.

Syntax and schema
Invalid knowledge type
Missing required field
Malformed reference
Duplicate stable ID
Unknown status
Referential integrity
Broken symbol reference
Missing document
Missing superseded item
Reference to deleted schema
Invalid owner
Authority conflicts
Two active canonical definitions for the same concept
Two decisions claiming authority over the same scope
Historical document included in default routing
Structural rules
Decision without consequences
Assumption without failure consequence
Invariant without scope
Rejected alternative without associated decision
Executable checks
Code example fails
Source-derived value changed
Referenced test no longer exists
Generated excerpt differs
Agentic linter

It should evaluate semantic quality.

Low information gain
“This function retries the request.”

The code already shows that.

Unsubstantiated intent
“We do this for performance.”

No evidence or decision context exists.

Redundancy

Two items express the same rationale.

Contradiction
Item A:
Ordering is guaranteed per account.

Item B:
Ordering is not guaranteed.
Scope ambiguity
“Requests are retried three times.”

Which requests? Which service? Which failure classes?

Incomplete decisions

The decision says what was chosen, but not why alternatives were rejected.

Obsolete rationale

The constraint that motivated a decision no longer exists.

Narrative decay

A long document contains unrelated decisions, assumptions, and historical notes that should be separated.

Linter outputs should be typed

Avoid generic warnings.

YAML
issue:
  type: possible-duplicate
  severity: warning
  items:
    - auth.stateless-validation
    - identity.token-local-validation

  explanation: >
    Both items appear to state that token validation avoids database access.

  suggested_actions:
    - merge
    - mark one contextual
    - narrow scopes
    - declare distinction
8. Change-impact and maintenance engine

This is the self-healing component.

It should not simply mark all related docs stale.

It should generate verification obligations.

Change classification

First classify the code change:

Rename
Move
Signature change
Behavior change
Default change
Schema change
Dependency change
Boundary change
Removal
New public surface
Internal refactor
Test-only change
Impact rules by knowledge type

Examples:

Decision

A refactor usually does not invalidate a decision.

But removal of the chosen mechanism may.

Constraint

A code change rarely invalidates an external constraint.

But an external API version change might.

Assumption

A change to event partitioning should trigger assumptions about ordering.

Invariant

Changes to enforcement points or tests should trigger verification.

Risk

A risky legacy path being removed may allow the risk item to be retired.

Intent

Behavior changes may require checking whether the original intent still holds.

Verification obligations

The engine should produce:

YAML
obligation:
  knowledge_item: auth.stateless-validation
  trigger:
    type: symbol-behavior-change
    ref: symbol:auth.verifyAccessToken

  question: >
    Does token validation still intentionally avoid synchronous persistence access?

  evidence:
    changed:
      - symbol:auth.verifyAccessToken
    unchanged:
      - decision:auth.stateless-validation

  required_outcome:
    - confirmed
    - updated
    - superseded
    - no-longer-applicable
    - uncertain
Confidence tiers
Mandatory
Recommended
Informational

Only strong, explainable dependencies should create mandatory obligations.

Coherence maintenance

The engine should also periodically look for corpus-wide decay:

Duplicate rationale
Contradictory guarantees
Orphaned knowledge
Items with no active scope
Decisions whose implementation disappeared
Assumptions with no recent validation
Risks attached only to deleted code
Canonical concepts with competing definitions

This can run on pull requests and as a periodic repository health check.

9. Repository workflows

The framework must fit naturally into development work.

Repository initialization

An onboarding agent scans the repository and proposes:

Domain boundaries
Canonical concepts
Likely invariants
Existing ADRs
Potential historical knowledge
Current docs worth importing
Docs that merely restate code

It should not automatically invent intent.

The result should be a migration plan, not a large generated corpus.

Planning workflow

When an agent receives a task:

1. Resolve relevant code targets.
2. Retrieve applicable knowledge.
3. Highlight constraints, invariants, and risks.
4. Identify contested or uncertain context.
Pull-request workflow

The pull request should include a documentation impact section:

Knowledge impact

Confirmed unchanged:
- auth.stateless-validation
- auth.revocation-delay

Updated:
- auth.token-guarantee

New:
- auth.refresh-token-rotation-constraint

Unresolved:
- none

“No impact” should be a valid outcome.

Review workflow

Review agents should verify:

The code still respects invariants.
The implementation matches active decisions or explicitly supersedes them.
New rationale is evidence-backed.
No duplicate canonical item was introduced.
Impacted obligations were resolved.
Incident workflow

Incidents often reveal undocumented knowledge.

After an incident, the framework should ask:

Did we discover a missing invariant?
Was an assumption false?
Was a known risk underestimated?
Did an operational heuristic change?
Should a decision be revisited?
Deprecation workflow

When a system path is removed:

Retire associated risks
Archive obsolete decisions
Supersede outdated guarantees
Remove invalid assumptions
Preserve only historically meaningful context
10. Governance and observability

The system needs governance because semantic documentation involves judgment.

Ownership model

Ownership can exist at several levels:

Domain owner
Knowledge item owner
Reviewer group
Subject-matter expert
Operational owner

Agents should not become the ultimate authority for business intent.

They can propose, organize, detect, and verify—but some items require human endorsement.

Trust model

Each item should record origin:

The first proof should demonstrate:

An agent changing code receives important non-obvious context before acting and is reliably prompted to update or verify only the knowledge that truly matters.

That is the core value.

The framework’s central lifecycle

Everything can be reduced to this loop:

Capture
    Preserve non-recoverable knowledge.

Attach
    Connect it to the concepts, boundaries, and implementation it governs.

Retrieve
    Give it to agents at the moment it affects a decision.

Challenge
    Re-evaluate it when relevant conditions change.

Resolve
    Confirm, update, supersede, archive, or mark uncertain.

Learn
    Improve relationships, routing, and linting from outcomes.

The system becomes fully fledged when all six stages are supported.

The strongest framing I see is:

A knowledge-contract framework for software repositories.

The codebase describes the system’s realized behavior. The knowledge layer preserves the intent, constraints, decisions, and guarantees that should govern how that behavior evolves.

A strong name should communicate three things:

this is about preserving non-code knowledge

it is meant for agents working inside repositories

it keeps intent, constraints, and decisions attached to evolving code

My recommended shortlist

I would narrow it to these six:

1. IntentGraph

2. Engram

3. Charter

Best conceptual framing.

My personal preference

I would probably choose IntentGraph for the framework itself and give individual parts separate names:

IntentGraph
├── IntentLang      authoring format
├── IntentLint      deterministic and agentic validation
├── IntentIndex     graph and retrieval layer
├── IntentSkill     agent instructions and interface
└── IntentCheck     pull-request impact workflow

That naming family is clear and coherent.

A more brand-oriented alternative would be:

Engram

├── Engram Lint

My strongest two are therefore:
